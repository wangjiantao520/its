# ITS 扣子云部署与 PostgreSQL 迁移设计

## 背景

ITS 当前使用 `better-sqlite3`，数据库文件默认位于项目目录下的
`data/quotation.db`。扣子生产部署会把代码作为只读运行产物加载，应用在模块初始化时又会打开数据库、启用 WAL 并执行迁移，因此所有依赖数据库的接口会在进入业务逻辑前返回 500。

最新构建已经验证 `better-sqlite3` 的 Linux 预编译文件仅要求 GLIBC 2.29，说明当前生产故障不再是 GLIBC 版本问题。继续使用部署产物内的 SQLite 仍然会面临只读目录、冷启动数据丢失、多实例数据不一致和原生模块兼容风险。

## 目标

- 让 ITS 在扣子生产环境中稳定启动并支持多实例运行。
- 保留现有管理员、成员账号、密码哈希、角色权限和 Cookie 登录流程。
- 完整迁移现有报价、配置、用户、会话、分享、审计和 AI 相关数据。
- 移除生产运行对 SQLite 文件和 `better-sqlite3` 原生模块的依赖。
- 保持现有页面地址和 API 响应格式兼容。
- 支持可重复执行的迁移、数据核对、失败回滚和后续版本升级。

## 非目标

- 本次不切换到 Supabase Auth。
- 本次不重做页面视觉设计。
- 本次不改变现有角色模型或业务审批流程。
- 本次不把数据库密钥暴露给浏览器，也不让前端直接访问数据库。

## 方案选择

采用 Supabase 托管 PostgreSQL。应用运行流量使用 Supavisor Transaction Pooler，数据库迁移、备份和一次性数据导入使用直接连接或 Session Pooler。

不采用以下方案：

- `/tmp` SQLite：冷启动、扩缩容或重新部署后数据可能丢失。
- 项目目录 SQLite：扣子生产产物不可写，已复现 `SQLITE_READONLY_DIRECTORY`。
- 扣子轻量单表数据库：现有系统包含多表关联、事务、版本、审计和权限查询，不适合作为本系统的关系型数据层。

## 总体架构

```text
浏览器
  -> Next.js 页面和 API（扣子云服务器）
     -> 服务端登录、角色鉴权和业务校验
        -> PostgreSQL 访问层
           -> Supabase Transaction Pooler
              -> Supabase PostgreSQL
```

浏览器只调用现有 ITS API。数据库连接串只保存在扣子服务端环境变量中，不使用 `NEXT_PUBLIC_` 前缀。现有会话令牌仍然以哈希形式保存在 `auth_sessions` 表中。

## 数据访问层

使用纯 JavaScript PostgreSQL 驱动 `postgres`，避免原生二进制和 GLIBC 依赖。生产连接配置必须满足：

- 从 `DATABASE_URL` 读取连接串。
- 启用 TLS。
- Transaction Pooler 模式下关闭 prepared statements。
- 设置较小的单实例连接上限、连接超时和空闲回收时间。
- 连接错误转换为统一 API 错误，并记录不包含密码的诊断信息。

建立单一数据库模块，提供异步的查询、单行查询、事务和健康检查接口。API、聚合服务、鉴权、会话、分享和迁移均通过该模块访问数据库，不再直接导入某个驱动实例。

数据库模块导入时不得执行建表、备份或数据写入。启动过程只完成配置校验；迁移由独立命令执行。

## SQL 与类型转换

现有表名和主要字段名保持不变，降低页面和接口改造风险。转换规则包括：

- `INTEGER PRIMARY KEY AUTOINCREMENT` 转为 PostgreSQL identity/bigint 主键。
- SQLite 整数布尔值统一转换为 PostgreSQL boolean，API 层继续输出兼容值。
- 时间字段统一为带时区时间或明确的 UTC 时间字符串。
- `INSERT OR IGNORE` 转为 `ON CONFLICT DO NOTHING`。
- SQLite `last_insert_rowid()` 改为 `INSERT ... RETURNING`。
- SQLite 日期、字符串拼接和动态占位符语法改为 PostgreSQL 等价写法。
- 金额字段继续采用精确数值类型，禁止浮点累计导致金额偏差。
- 为用户、会话、报价归属、分享令牌、状态、创建时间等高频查询补齐索引和唯一约束。

迁移脚本应显式创建外键及删除行为，不依赖 SQLite 的宽松类型和隐式转换。

## 数据迁移

迁移分为四个阶段：

1. 备份与冻结
   - 对现有 `quotation.db` 执行完整性检查。
   - 生成带时间戳的 SQLite 备份并验证备份可打开。
   - 导出所有表的行数、主键范围和关键业务金额汇总作为迁移基线。

2. 建立 PostgreSQL 结构
   - 使用带版本号的 SQL migration 创建表、索引和约束。
   - 使用 PostgreSQL advisory lock 防止扣子多个实例并发执行同一迁移。
   - 在 `schema_migrations` 中记录已成功执行的版本。

3. 导入数据
   - 按外键依赖顺序批量导入。
   - 在单次迁移事务中处理每个逻辑数据组。
   - 保留原主键、账号密码哈希、令牌哈希、创建时间和业务编号。
   - 导入完成后同步 identity sequence，避免新记录主键冲突。

4. 核对
   - 比较每张表的行数、空值数量和主键范围。
   - 核对用户数量、角色、启用状态和默认账号。
   - 核对工程报价、维护报价、历史版本及关键金额合计。
   - 随机抽查报价明细、分享记录、审计日志和 AI 会话。
   - 只有全部核对通过才允许切换生产连接。

迁移工具默认只读 SQLite、只写目标 PostgreSQL；重复执行时必须安全退出或以明确的覆盖参数运行，禁止静默重复导入。

## 应用改造范围

- 将同步数据库调用改为异步调用，并更新所有相关 API 和服务函数。
- 保留当前 `{ success, data?, error? }` 响应结构。
- 保留当前登录 Cookie 名、过期规则、哈希令牌和 401/403 行为。
- 将数据库初始化和默认数据写入改为显式 seed/migration，禁止 API 模块导入时写库。
- 删除 `better-sqlite3`、类型包和预编译下载脚本。
- 停止跟踪运行时数据库文件，保留迁移前备份但不提交到 GitHub。
- 更新 `.env.example`、构建脚本、启动脚本和扣子部署说明。

## 扣子环境配置

生产环境至少配置以下变量：

- `DATABASE_URL`：Supabase Transaction Pooler 连接串。
- `DATABASE_MIGRATION_URL`：迁移使用的直接连接或 Session Pooler 连接串。
- `SESSION_SECRET`：服务端会话安全密钥。
- `DATABASE_POOL_MAX`：单实例最大连接数，使用保守默认值。

启动顺序为：配置校验 -> 获取迁移锁并执行待执行迁移 -> 数据库健康检查 -> 启动 HTTP 服务。任何步骤失败都应输出明确日志并终止启动，不能以半可用状态接收请求。

## 安全设计

- 数据库密码和服务端密钥只存放在扣子环境变量与本地忽略文件中。
- 不在客户端加入 Supabase secret/service key。
- 应用数据库角色仅获得 ITS 所需表的权限。
- 数据表不直接暴露给匿名 Data API；所有业务访问继续经过 ITS 服务端鉴权。
- 日志必须过滤连接串、密码、Cookie 和会话令牌。
- 迁移完成后轮换临时导入凭据。

## 失败处理与回滚

- PostgreSQL 切换前保留原 SQLite 备份和迁移基线报告。
- 迁移失败时回滚当前事务，不修改生产连接变量。
- 部署失败时回滚到上一扣子版本；数据库 migration 只允许向前且保持向后兼容一个应用版本。
- 切换后发现严重问题时，停止写入、导出故障期间新增记录，再按明确脚本回迁或修复后重放。
- 不以重新上传旧 SQLite 文件作为长期回滚方案。

## 测试与验收

自动化测试覆盖：

- PostgreSQL migration 首次执行和重复执行。
- SQLite 到 PostgreSQL 的表行数、主键和金额核对。
- 管理员、普通成员和未登录用户的登录与权限边界。
- 工程报价、维护报价、历史版本、审核、分享和统计聚合。
- 会话创建、验证、过期、退出和并发请求。
- 数据库断开、超时和异常返回。

交付前必须通过：

- 代码检查、类型检查、生产构建和自动化测试。
- 本地 PostgreSQL 集成测试。
- 扣子预览环境数据库连通测试。
- 扣子正式域名登录及主要业务流程回归。
- 所有动态 API 不出现未预期的 500，页面无永久“加载中”。
- 数据迁移核对报告全部通过。

## 实施顺序

1. 建立 PostgreSQL 测试环境和数据库抽象层。
2. 编写 PostgreSQL schema migration 与 SQLite 导入器。
3. 迁移鉴权、会话和用户接口，先打通登录闭环。
4. 迁移报价、配置、分享、审计和 AI 相关接口。
5. 完成全量自动化测试和本地生产验证。
6. 创建并备份正式 Supabase 数据库，执行全量数据迁移与核对。
7. 在扣子配置安全变量，部署并执行正式回归。
8. 确认稳定后移除 SQLite 生产依赖和旧兼容脚本。

## 完成标准

系统只有在现有业务数据完整保留、扣子正式域名可登录、所有主要页面和操作可用、权限边界正确、生产构建与自动化测试通过，并且重新部署后数据仍然存在时，才视为迁移完成。
